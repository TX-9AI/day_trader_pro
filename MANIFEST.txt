consolidate_trades_datefilter_2026-07-28 — day_trader_pro (CONTROL BOX repo)

NOTE: this is the day_trader_pro repo, NOT options_trader_v3.

THE BUG (upstream defect Z, mechanism now confirmed):
  harvest copies each box's ENTIRE trades.db into trades/<date>/, and
  _read_table ran a bare `SELECT * FROM trades` with no date filter. So every
  night's fleet_trades_<date>.json/.csv contained that box's WHOLE history, not
  the day's trades. The files are cumulative archives:
      fleet_trades_2026-07-20.csv  137 rows
      fleet_trades_2026-07-24.csv  230 rows
      fleet_trades_2026-07-28.csv  266 rows
  Every per-day metric read off them silently blended weeks — win rate, net P&L,
  strategy mix, and the regime_conviction distribution. It also masked how rare
  the butterfly is: "3 butterflies" in the 07-28 file is 3 EVER (07-09, 07-20,
  07-24), not 3 that day.

THE FIX (v1.2):
  _read_table(conn, table, date=None, date_col=None) filters with
  `WHERE <date_col> LIKE '<date>%'` — but ONLY when the column actually exists on
  that schema, checked via a `LIMIT 0` describe first. An older DB missing the
  column reads in full rather than silently returning zero rows.
  Call sites, with the REAL column names (verified against trade_logger.py, not
  guessed — the first pass had these wrong):
      trades                  -> entry_time
      regime_log              -> logged_at
      circuit_breaker_events  -> event_time
  RTH is 13:30-20:00 UTC so a UTC date prefix matches the ET session date.

PROVEN (standalone, synthetic DB):
  4 rows across 3 dates -> unfiltered 4, filtered to 2026-07-28 = 2
  regime_log filtered by logged_at = 1
  table WITHOUT the date column      -> reads in full (safe degradation)
  missing table                      -> ([], []) unchanged
